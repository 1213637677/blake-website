秒剪用到的 AI 能力来自多个不同的推理服务：抠图、视频抠像、色彩自适应等。它们部署在不同的服务上，有的走统一推理框架、有的走 ComfyUI 工作流，请求体格式也各不相同。

`mmvaitoolssvr` 是这些能力的统一入口。它对上只暴露两个接口——`SubmitTask` 和 `GetTask`——用一个 `task_type` 字段区分能力类型，对下按注册表找到真正的服务并转发。

这个服务自己不做推理、不持有任务状态，只做三件事：**路由、透传、取结果**。

## 核心流程

### 两个接口覆盖所有能力

```text
SubmitTask(task_type, task_data) -> 下游 /submit_task 的返回原文
GetTask(task_type, {"task_id": ...}) -> Redis 里的结果 JSON
```

任务提交后立刻返回 `task_id`，推理在下游异步进行，结果由下游写回 Redis。本服务的 `GetTask` 不调下游，直接按 key 读 Redis——**查询这一步完全不触碰推理服务**。

这个分工让查询变得很轻：客户端可以放心地轮询，压力落在 Redis 而不是推理集群上。

### task_type 到下游寻址名的推导

`task_type` 是一个逻辑标识，不直接等于服务名。真正的下游寻址名按三级推导：

```text
命中任务定义 → polaris_name 不为空   -> 用 polaris_name
命中任务定义 → polaris_name 为空     -> 用 service
未命中任务定义                        -> 用 task_type 自身
```

第三级是兜底：注册表里没有的类型，就当它自己就是服务名。这让新增能力可以先不注册、直接按服务名调用，注册只是为了拿到更好的名字和后端类型。

匹配任务定义时先按 `TaskId` 全量扫、再按 `Service` 扫，且 `TaskId` 命中立即停止。`TaskId` 是唯一的，`Service` 可能与别的任务的 id 撞名，所以 id 优先——顺序反了会出现路由到错误下游的情况。

### 任务注册表是外部写入的只读副本

任务定义不由本服务维护，由另一个服务写进 Redis，本服务只读：

```text
mmvaitoolssvr_task:{id}      单个任务定义（string）
mmvaitoolssvr_task_index     全部 id 的索引（zset）
```

启动时拉全量，之后每 10 秒刷一次本地 `sync.Map`，并删除索引里已不存在的任务。

10 秒的刷新间隔意味着**新增能力最多 10 秒后生效**，不需要重启网关。代价是注册表与本服务之间没有版本协调——注册表结构变了（比如加了字段），本服务的结构体要同步改，否则解析出的字段为空。

清理逻辑是必要的：只增不删的话，下线一个能力后它的定义会永远留在本地缓存里，路由仍然指向一个已经不存在的服务。

### 两种后端的请求体处理

任务定义里有一个 `backend` 字段区分后端类型：

| backend | 处理方式 |
|---|---|
| `native` | `task_data` 原样透传 |
| `comfy` | 注入 `workflow` 字段（值为该任务的 service）再转发 |

ComfyUI 的执行单元是工作流，所以多注入一个字段告诉它跑哪个工作流；统一推理框架不需要，按其 bundle 机制执行。

注入发生在 JSON 层面：先反序列化、加字段、再序列化。JSON 解析失败时原样透传，不因为注入失败而拒绝请求——让下游自己决定是否报错。

### 结果 key 的构成

`GetTask` 的 key 是 `{route_name}_{task_id}`。

值得注意的是这里用的是**推导后的路由名**，不是原始的 `task_type`。两者在大多数情况下相同，但当 `task_type` 命中注册表且声明了 `polaris_name` 时就不一样了。用路由名拼 key，是为了与下游写回结果时用的 key 保持一致——下游只知道自己的服务名。

这意味着 `task_type` 到路由名的映射**在提交和查询两次调用之间必须稳定**。如果这中间注册表被改了（比如改了 polaris_name），提交时和查询时算出的 key 不同，结果就永远读不到。10 秒刷新间隔让这个窗口变得很窄但确实存在。

## 设计与取舍

**只暴露两个接口，用数据字段区分能力。** 新增能力不需要改接口定义、不需要改路由表，只要在注册表里加一条。代价是类型安全完全丧失——`task_type` 和 `task_data` 都是字符串，拼错了只能在下游暴露。

**查询不碰推理服务。** 结果由下游写回 Redis，网关只读 Redis。好处是轮询成本极低，推理集群不被查询流量打扰；代价是网关无法感知"任务还在跑"和"任务不存在"的区别，读不到就返回 `task not found`。

**注册表是外部写入的只读副本。** 好处是能力注册与网关部署解耦，新增能力不需要动网关；代价是两个服务要共享同一份结构体定义，且刷新间隔决定了变更生效的延迟。

**路由名推导三级兜底。** 未注册的类型按自身寻址，让"先上线后注册"成为可能。代价是拼写错误的 `task_type` 不会报"能力不存在"，而是去做一次注定失败的服务寻址。

**提交同步、取结果异步。** Submit 直接转发并等待下游返回（下游自己入队后立刻回），Get 读 Redis。这个组合要求下游必须把结果写回同一个 Redis，是本服务与下游之间的隐式契约。

## 后续优化方向

**`task_type` 拼错无法在网关层发现。** 未注册的类型会走到"按自身寻址"的兜底分支，最终表现为一次失败的服务寻址而不是明确的"未知能力"。可以在未命中注册表且寻址失败时返回更明确的错误。

**提交与查询之间的路由名漂移。** 两次调用之间如果注册表变更导致路由名变化，结果 key 会算错。窗口是 10 秒，但可以让提交时把算出的路由名回传给调用方，查询时直接带上来。

**注册表结构与外部服务强耦合。** `Task` 结构体必须与写入方保持一致，字段增减需要两边同步改。当前没有版本字段或 schema 校验，解析出空字段不会报错。

**结果读取没有过期与清理。** `GetTask` 只读不写，任务的过期与删除完全由下游和 Redis 的过期策略决定，网关不知道一个 task_id 是否还有效。

**刷新失败只记日志。** `refreshTaskCache` 出错时返回错误并在下个周期重试，期间本地缓存保持旧值。持续失败会让注册表长期停在某个旧版本且没有告警。

## 外部依赖与系统边界

- **任务注册表由另一个服务写入 Redis**，本服务只读，其结构与写入时机由该服务决定，两边的结构体定义必须同步演进
- **下游推理服务按 bundle 或工作流执行**，各自的处理耗时、并发上限与失败模式不同，网关不感知这些差异，也无法对慢能力单独限流
- **结果由下游写回 Redis**，写入的 key 格式与时效是网关与下游之间的隐式契约，契约破坏的表现是"任务查不到"而非报错
- **服务寻址依赖 Polaris**，开发环境走另一套代理，寻址失败时网关直接返回错误，没有备用地址或重试
- **统一推理框架与 ComfyUI 两类后端的能力范围由各自决定**，网关只能通过 `backend` 字段区分注入行为，无法校验请求体是否符合后端预期
