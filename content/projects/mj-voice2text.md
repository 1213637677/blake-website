秒剪的字幕功能分两段：语音转文字由外部的转写服务完成，产出带时间戳的分句与词；本服务（`mmvnlpsvr` 的 voice2txt 模块）负责后一半——把转写结果加工成**可渲染的字幕**，包括断行、高亮、贴纸和字号。

加工这一步是纯 CPU 与规则计算，但要拉三个外部能力：词性与命名实体识别、音量分析、声音事件检测。所以服务的核心设计问题不是算法，而是**怎么把多个耗时不同的外部调用组织进一个轮询接口里**。

## 核心流程

### 两段处理与进程内任务态

一次字幕任务的状态分两处存放，对应两个阶段：

```text
runningTask   concurrency map，voiceId -> 任务    // 转写已完成，正在做高亮
finishedTasks KVCache，TTL 1 小时                 // 已完成，缓存一段时间
```

转写阶段服务端不持有状态，直接把轮询转发给转写服务。转写进度到 100 时才在本进程里建任务、起一个 goroutine 做高亮，任务放进 `runningTask`。高亮完成后从 `runningTask` 摘除、写进 `finishedTasks`。

`runningTask` 是进程内的并发 map，不跨实例共享。这意味着**轮询必须落在同一个实例上**——客户端拿着 voiceId 轮询时如果打到另一台机器，那里既没有 `runningTask` 也没有缓存，会重新去问转写服务。这决定了这个服务不能有随机负载均衡，或者必须接受轮询落到别处时的重复计算。

已完成任务缓存 1 小时，是为了让重复打开同一段视频不必重算。缓存过期后临时音频文件由一个延迟任务删除，延迟时间比任务缓存多 2 分钟，保证先删缓存再删文件。

### 进度是推算出来的

客户端要一个进度条，但两段处理的耗时无法准确预估，也没有真实的完成百分比。所以进度是分段硬编码的：

```text
转写阶段：  progress = 上游进度 - 上游进度 / 10     // 转写占 90%
高亮阶段：  progress = 95                          // 固定
完成：      progress = 100
```

高亮阶段恒返回 95，不假装知道进行到哪一步。这个"假进度"是刻意的：与其算一个抖动的数字，不如卡在一个固定值上，到点直接跳 100。

### 断行：按字宽拼词成句

转写服务返回的是分句，每句带词数组和每个词的起止时间。字幕要求每行不超过 N 个字，所以要把长句再切开。

切分按词累加字宽，累计长度达到上限就断一行，行首记录该词的起始时间。短句（整句短于上限）直接成一行，不做处理。

两个细节：英文单词前补一个空格，避免中英混排时词粘在一起；句末的问号要归属到最后一行——断句时标点单独成词，不处理的话会出现一个只有标点的空行。

断行结果带完整的字级别时间戳，这是后面所有高亮能对齐到字的前提。

### 高亮规则：关键词 + 词性 + 音量

高亮是一组规则，每条规则产出一种类别的高亮。规则按类别叠加，一句话可以同时有多个高亮。

| 规则 | 触发条件 | 产物 |
|---|---|---|
| 逐字高亮 | 长句占比低于阈值 | 整句按字高亮 |
| 惊叹词 | 命中关键词且不是句末词 | 随机位置贴纸 |
| 关注引导 | 命中关键词或包含用户名 | 固定位置贴纸 |
| 点赞引导 | 命中关键词 | 随机位置贴纸 |

逐字高亮有条件：先统计所有原始分句里"长度超过 11 字的句子"的字数占比，占比低于 0.6 才启用。长句太多时逐字高亮会让整屏都在闪，所以按句式分布决定要不要开。

**字号由音量决定**。每句的音量与全篇平均音量比较：高于 1.2 倍放大到 130%，低于 0.8 倍缩到 80%，其余 110%。这样配音的轻重会体现在字幕大小上。

音量分析要读音频文件，耗时明显长于其他调用，所以它是**先发起、后取结果**：在规则计算开始前就起一个异步任务，规则跑完再取。取不到时（文件缺失或分析失败）所有高亮统一用 110%，不因为音量失败而丢掉高亮。

### 三个外部调用的并发组织

词性识别、音量分析、声音事件检测三者互不依赖，用 promise 封装后并行发起，谁先跑完谁先存结果，需要时再取。

promise 在这里的作用不是简化异步写法，而是**让"发起"和"取结果"可以在流程的不同位置**——耗时最长的那个在流程最开始就发起，中间做不依赖它的规则计算，最后统一取。串行发起的话总耗时是三者之和，并行后只等于最慢的那个。

词性识别用于几条语言规则：连续三次重复、无意义数字、副词形容词组合、关心的命名实体。这些规则服务的是"哪些词值得强调"，是纯规则而非模型判断。

## 设计与取舍

**任务态放在进程内，不跨实例共享。** 好处是不需要一个共享存储来放中间态，轮询命中同一实例时最快。代价是轮询落点被绑定：打到别的实例会重新走一遍转写轮询，且第二阶段的重复计算无法被识别。

**已完成任务缓存 1 小时，而不是持久化。** 字幕结果是可重算的，缓存只为省一次重复计算，不值得为此建表。代价是过期后重复打开同一视频要重算，且重算依赖转写服务仍保留该 voiceId 的结果。

**进度是假的，且不掩饰。** 高亮阶段恒定返回 95。代价是进度条在这一段完全不动，用户体验上是"卡住"；好处是不会有进度回退——真实的百分比在多规则并行时很容易算出个抖动的数。

**高亮规则是硬编码的规则集，不是可配置的策略。** 关键词表、阈值（11 字、0.6）、缩放比例（1.2/0.8 倍）都写在代码里。代价是运营想调高亮策略要发版；好处是规则简单直白，且不需要一套策略配置系统。

**音量失败降级而不是失败。** 取不到音量时所有高亮用默认字号，高亮本身照常产出。这符合字幕的定位——高亮是增强，没有它字幕仍然可用；因为增强失败而让整个字幕失败是本末倒置。

**并行靠 promise 而非固定的流水线顺序。** 三个外部调用耗时差异大，固定顺序会让总耗时等于三者之和。代价是取结果的时机散落在流程里，读代码时不如串行直观。

## 后续优化方向

**轮询与实例绑定的问题没有解决。** `runningTask` 是进程内结构，多实例部署下轮询落到不同实例会重复计算。要么做会话粘滞，要么把中间态移到 Redis——后者会让"高并发 map"的性能优势消失，需要权衡。

**高亮规则与阈值硬编码。** 关键词表、句式占比阈值、音量缩放比例都不可配置，运营调整需要发版。这类策略参数适合放到云控配置里。

**只有一套高亮规则在生效。** 常量里定义了两套规则（短剧与测试），测试规则那条路径带着声音事件的调用，但没有运营可选择的规则体系——新增规则要改 `switch` 分支。

**临时文件的清理依赖延迟任务。** 用延迟消息在 1 小时 2 分后删文件。延迟任务丢失会留下孤儿文件，且没有兜底的定期扫描。

**转写服务的进度语义被直接透传。** 上游进度的准确性决定了前 90% 的进度表现，本服务只是做了个除法换算，没有平滑或校准。

## 外部依赖与系统边界

- **语音转写由外部服务完成**，本服务只消费其分句、词与时间戳，转写的准确率与语言支持范围直接决定字幕质量
- **词性与命名实体识别由内部服务提供**，其识别粒度决定了语言类高亮规则（重复、副词形容词、命名实体）的可用范围
- **音量分析需要读取本地音频文件**，音频由转写前的上传环节落在本地盘，文件缺失时该路高亮降级
- **贴纸素材的 ID 从云控配置读取**，配置缺失时贴纸类高亮的 ID 为空，高亮仍产出但客户端无素材可渲染
- **临时文件存放在本地磁盘**，服务多实例部署时文件与任务态一样不跨实例共享
