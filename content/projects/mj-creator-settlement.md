运营在后台发布有奖征稿活动，创作者报名后用秒剪剪完视频发到视频号，运营审核通过，系统按月出账单打款。

服务在秒剪网关后面是一个独立的 Go 服务。征稿主链路之外，账号入驻审核、创作者标签、邀请码、教程课程、站内信和月度账单也在同一个服务里；定时清理和出账则拆成独立进程部署，重活不占在线接口的资源。

一次参与有 11 个状态、19 种迁移动作。从视频发布到账单对创作者可见，中间隔着 7 天冻结期和一次按月出账，实际要跨两个自然月。

## 核心流程

### 从领到发，再到审

创作者报名领任务，系统建一条参与记录（execution），状态是 `Working`。用秒剪剪完分享到视频号后，客户端上报一段本地文件的哈希，进入 `Submitted`。

此时系统还没拿到视频号那边的实体 ID。绑定成功后进 `Auditing`，运营在后台看视频决定过不过：

- 通过 → `Approved`，进入 7 天冻结期
- 不通过 → 没到次数上限就是 `Denied`，改完能重提；累计拒绝 2 次就是 `Failed`，这期活动不能再领

冻结期结束再复查一次视频状态，没问题进入 `Accounting` 待出账，次月出账。

*参与状态流转，含全部失败与回滚分支*

### 每一步都留痕

状态历史表记录每一次迁移：变化后的状态、动作类型、操作人、视频号 objectID，外加一个 JSON 字段存当时的上下文（审核意见、拒绝次数、视频描述、截图、查重结果）。

这是朴素版的事件溯源。做结算业务，"什么时候、谁、把状态从什么改成了什么"是刚需——创作者来问收益为什么没到账，唯一能回答的就是这张表。

状态变更和历史写入在同一个事务里：要么状态变了且有记录，要么都没发生。不会出现"状态改了但没留痕"——对结算系统来说，没有记录的状态变更等于说不清。

### 状态变更的并发安全

所有改变状态的操作都是同一个套路：**加锁，拿锁后重新读一次，再校验状态**。

```
lock(unionID)
defer unlock

// 拿锁后重新读，等锁期间状态可能已被改
exe = reload(exe.ID)
if exe.status != AUDITING:
    return error
```

第一次读是为了拿到 unionID（锁的粒度是 unionID），第二次读才用于判断。等锁期间状态可能已经被别的请求改了，不重读就是基于过期数据做决策。

锁时长 2 秒，配合线性退避最多重试 10 次——这个参数反过来说明临界区必须很短：锁里只做状态校验和一次事务写，绝不调远程接口。

限量活动的名额扣减还要靠数据库行锁兜底，条件直接写在 SQL 里：

```
UPDATE task SET join_count = join_count + 1
WHERE id = ? AND join_count < count
-- 影响行数为 0 即名额已满
```

先查后写的话，两个请求同时读到"还剩 1 个"就都放行了。

### 结算：三个时间概念

账单这块最容易搞混的是**三个不同的时间**：

1. `submit_time` —— 视频在**视频号发布**的时间，不是审核通过的时间
2. `finish_time` —— 冻结期结束时刻 = `submit_time + 7 天`
3. `bill.month` —— 算哪个月的账，**按 submit_time 归月**

出账任务每月 8 号跑，扫上个月区间内处于 `Accounting` 且还没关联账单的记录。查询条件里的 `账单ID 为空` 就是幂等的落点——已关联的不会再被扫到，重跑不会产生第二张账单。函数注释写明了这个契约：`此函数的执行可能会被中断, 必须保证幂等和可重入`。

8 号这天连跑三次（10 点、11 点、12 点），注释写着"重试两次防止失败"。月度出账一年只有 12 次机会，失败一次要等一个月。

账单生成后要到次月 10 号才对创作者可见，中间留出打款和对账的窗口，避免创作者看到金额但钱还没到。

### 后台与运营侧

活动增删改、暂停恢复、手动排序（独立的 position 表，支持运营随时调顺序）、限量配置、标签定向（活动带等级与领域标签，创作者带标签，取交集决定可见性，空表示不限）、邀请码管理、各类 CSV 导出。

活动分页有个细节：不能用"上一页最后一个 ID"做游标，因为运营会随时调整顺序。改成客户端回传已展示的 ID 列表，服务端做差集。

## 设计与取舍

### 视频文件 hash 映射视频号视频 id

创作者在秒剪里剪完直接分享到视频号，跨应用**拿不到视频号返回的实体 ID**，客户端能上报的只有本地文件的哈希。

但奖励必须绑定到那个 ID。没有它就无法验证视频是否真实存在、是否公开、有没有违规——后续审核和风控全部无从谈起。

更麻烦的是视频号侧索引有延迟，刚发布就是查不到。**这不是抖动，是确定性的延迟**。

这个约束把设计带偏了方向：**重试不是容错手段，而是主流程的一部分**。系统必须假定"第一次一定查不到"。

于是有了三层兜底：

| 层 | 做法 |
|---|---|
| 第一层 | 投进延迟队列，每 5 分钟重试，最多 24 次（约 2 小时） |
| 第二层 | 每天定时扫描，补偿重试也没绑上的 |
| 第三层 | 后台人工绑定 |

![文件指纹三层兜底](/diagrams/09-bind-flow.svg)
*文件指纹三层兜底*

**消费端的关键判断只有一条：重试解决不了的才确认。**

```
unmarshal_failed        -> ACK   // 格式错了，重试一百次也一样
remote_call_failed      -> RETRY // 说不定下次就好了
video_found             -> ACK
not_found && tries_left -> RETRY // tryCount += 1，重新入队
not_found && no_tries   -> ACK   // 放弃治疗，转人工
```

这条判断看着简单，却是整个兜底能不能成立的关键。把可恢复的错误也确认掉，任务就静默丢失了——创作者提交了视频，系统在后台悄悄放弃，没人知道。

**重试必须有上界**：24 次后转人工，否则一条永远查不到的视频会无限占用队列。第二层扫描不按时间过滤，注释写明了原因：`防止出现任务截止时间延长导致不能自动绑定等情况`——运营往后调截止时间是常规操作，按时间过滤会漏。

三个入口（队列重试、定时扫描、后台人工）共用同一个绑定函数，幂等靠状态前置校验实现：不是 `Submitted` 就直接返回，谁先成功后面都是空转。

### 收益冻结期

审核通过不立刻结算，等 7 天**再查一次视频状态**——有没有被删、改成私密、或被判违规。

防的是"拿完奖励就删视频"。复查时重新拉取视频号上的公开标志位，违规判定用位掩码区分了"仅自己可见"和"所有人不可见"两种处置。

命中就撤销收益，并且**发短信告诉创作者具体原因**——是删了、私密了、还是违规了，文案各不相同。这点值得记：风控动作一定要给明确反馈，否则创作者只会觉得平台吞了钱。

**冻结期终点怎么算是个容易踩的坑。** `finish_time` 不是"审核通过时间 + 7 天"，而是**"视频号发布时间 + 7 天"**，而且进入结算时不再修改它：

```
finish_time = submit_time + 7d
// 进入结算时不改写 finish_time，防止执行时间误差导致延迟到下个月结算
```

如果按"定时任务实际跑的时刻"写，晚跑几分钟就可能把本月的收益推到下个月的账单里。以发布时间为锚点是确定性的，不受调度抖动影响。

（源码注释里写的是"以过审时间为准"，但实际取的是发布时间——注释和实现对不上，这点值得留意。）

### 退回是分岔，不是失败

真正复杂的不是主链路，而是各种失败和回滚路径。其中有个设计值得单独说：**退回时不无脑失败，先判断活动过期没有**。

```
if now < task.expire_time:
    exe.status = APPLIABLE // 还能再来一次
else:
    exe.status = EXPIRED   // 这期结束了
```

放弃任务、冻结期复查发现视频被删、后台判定"根本没发到视频号"，走的都是这套判断。

对创作者来说这两者体感差别很大：一个是"还能补救"，一个是"这期结束了"。能用同一段代码表达这个语义，比在各处散落 if 好维护得多。

**复用记录而不是新建。** 创作者放弃后重新领取，复用同一条 execution 只改状态。这是被业务倒逼的：一个 unionID 对同一活动只能领一次，用新记录就得靠历史反查，很快变成难以维护的判重逻辑。代价是重新领取时必须把残留清干净——文件哈希、查重状态、截图、文案，漏一个就串味。

**过期不是实时算的**，靠每分钟跑一次的定时任务批量刷，注释写得很直白：`任务过期, 数据库不会实时更新`。实时计算意味着每次查询都拿当前时间比，扫全表代价远高于每分钟刷一遍。活动还有个 `expire_cleaned` 字段标记"这批刷完了"，避免重复处理。

离线进程只跑定时任务和延迟队列消费，和在线接口在资源上互不影响。

### 多平台投稿的审核材料

活动不只收视频号投稿，还可以要求提交朋友圈截图或外站链接。这两类材料有独立的提交与审核状态，和视频状态并行推进。

活动截止清理时逻辑要分开处理：视频号投稿看视频状态，朋友圈和外站投稿看材料有没有提交——**已提交视频但没交截图**的，截止时一并判过期。

### 实现中的坑与边界

**放弃任务要清文件哈希。** 不清的话，同一创作者放弃后又提交同一段视频，哈希相同，绑定时会命中旧的记录。注释写的是"防止其他任务提交相同视频后绑定失败"。这种"数据残留导致的跨任务污染"很隐蔽，测试时不容易覆盖到。

**Redis 映射表的自愈。** 客户端提交时只有端上登录标识，没有 unionID，所以 Redis 里维护了一张「端上标识 → 参与记录」映射。这张是缓存，可能整体丢失，处理方式是在每次读写前检查 key 是否存在，不存在就从数据库重建；重建同样用 check-lock-check 防止多个协程重复建，还塞了个占位符防止缓存击穿。

**通知不能拖慢主流程。** 审核通过、拒绝、冻结期撤销都要发短信，全部扔进 goroutine 并带 recover。短信是旁路，失败不能影响状态流转。所有定时任务入口也都有 recover——一个 panic 不能让整个 cron 进程挂掉。

**登录态与敏感信息。** 客户端拿 JWT 换身份，payload 里再套一层 AES 加密。身份证号、银行卡号单独加密存储，密钥与 JWT 密钥分开。

**注销的拦路检查。** 创作者申请注销时先检查有没有未结算的钱和进行中的活动，有的话把具体原因返回前端——"创作收入尚未结清"或"有正在参与中的活动"。缺了它就会出事故：账号注销了钱还没结完，或者活动还挂着人没了。注销走"申请待删除"中间状态，满 15 天才允许真正清理。

**JSON 字段的边界。** 业务字段变动频繁（审核意见、各种标志位），用 JSON 扩展字段省掉大量 migration，靠 ORM 钩子自动反序列化。代价是这些字段没法做索引和 SQL 过滤，所以**需要查询和索引的一定是独立列**（状态、文件哈希、objectID、提交时间、结束时间都有索引），JSON 里只放展示用的东西。这个边界一开始就得划清楚，后期迁移很痛。

## 后续可以做的事

**三层兜底仍有缺口。** 如果视频号索引延迟超过 2 小时，或者视频被平台判定异常导致永远查不到，就只能靠人工。应该加"长期未绑定"的监控告警，而不是被动等运营自己去后台翻。

**过期状态靠批量刷有窗口。** 两次执行之间状态是滞后的。如果这个状态会直接展示给用户，展示时应该实时算一下。

**7 天冻结期和 30 次月度上限是硬编码常量。** 这类业务规则应该可配置化，便于根据作弊情况动态调整，不然改一次要发一次版。仓库里也留了注释：`这个文件里的配置之后要移到云控`。

**拒绝次数上限的语义可以更清楚。** 现在是"累计拒绝 2 次即失败"，但创作者视角看到的是"还能改几次"，这两个数字的换算在前后端各写了一遍，容易对不上。

**查重结果目前只展示不拦截。** 相似度存进扩展字段供运营人工看，没有自动拦截。要自动化的话需要一个阈值策略和申诉通道，光有数据不够。

**账单可见时间是硬编码。** 可见时间算的是次月 10 号，这个窗口的假设（打款需要多久）应该来自配置或实际打款状态，而不是常量。

## 补充说明：本模块读不到的部分

- **视频号侧的反查接口实现不可见**——只能看到调用与结果处理，无法确认索引延迟的具体分布，因此 5 分钟 × 24 次的参数是基于经验而非实测
- 视频状态复查依赖视频号接口，其判定逻辑不可见；违规标志位的完整语义也没有文档
- 实际打款环节的第三方转账实现不在本仓库，账单状态推进到"已结算"的接口目前是关闭的
- 查重（视频相似度）的计算由消息消费端回写，算法不在本服务内
- 客户端如何用端上标识换取提交入口的完整链路不可见，只看到服务端的映射查询
