素材下发的读写比极读倾斜：请求密集，运营一天可能只发布几次。所以读路径必须落在进程内存里，不能每次回数据库。

整个服务把这个需求收敛成了两个原语，都在公共库里，加起来不到 260 行：`ObjectCache` 与 `KVCache`。业务侧不自己实现缓存，只在这两者之间选一个，并提供一个 getter。

两者真正的差别不在"整对象 vs 分桶"，而在**键空间是否封闭**：能不能一次把要缓存的东西全量装进来。

## ObjectCache

一个缓存实例只装一个对象，用 `atomic.Value` 承载，读路径无锁。

```text
Get():
    data = atomic.Load()
    if data != nil: return data          // 快路径，无锁
    lock()
    data = atomic.Load()                 // check-lock-check
    if data == nil:
        data = getter()
        atomic.Store(data)
    unlock()
```

未命中才加锁，且加锁后再读一次。这样并发的未命中请求只有一个真正执行 getter，其余拿到已填充的结果。

`SetupObjectCache` 时传了 `interval > 0`，会额外起一个 goroutine 按间隔 `Reload`。`Reload` 与 `Get` 共用同一把锁，所以重载期间读请求会短暂阻塞在锁上——这是整对象替换的代价，换来的是读路径零分配、零查找。

重载失败时保留旧值：getter 返回 error 就直接返回，`atomic.Value` 里还是上一版数据。缓存不会因为一次回源失败而变空。

它的约束是**getter 必须能一次加载全量数据**，且这个全量要放得进内存。适合的数据形态是：一张配置表的全部行、一个面板的完整排序、一份全量索引。

## KVCache

基于 `ccache`，按 key 分桶存储，每个键独立 TTL。构造参数是三个：桶数、最大条数、每次淘汰条数，业务里基本是 32 桶、5000 到 10000 条、每次淘汰 16 到 128 条。

分桶是为了把全局锁拆成 32 把，不同 key 的写入互不阻塞。

`Fetch` 是标准读路径：命中且未过期直接返回；未命中走 `singleflight` 按 key 合并，同一个 key 的并发未命中只有一次回源。

```text
Fetch(key):
    item = bucket(key).Get(key)
    if item != nil && !item.Expired(): return item
    return singleFlight.Do(key, func() {
        val, ttl = getter(key)
        bucket(key).Set(key, val, ttl)
        return val
    })
```

单飞只合并同 key。不同 key 的并发未命中会各自回源——所以 `KVCache` 适合单键回源成本可控的场景，不适合"未命中就要扫全表"的场景。

TTL 由 getter 自己返回，每个键可以不同。批量场景另有 `MultiFetch`，把未命中的键收集起来一次查回，刻意不走单飞——批查询本身就是一次请求，再按 key 合并反而多此一举。

它还有一条与 `ObjectCache` 相反的语义：**回源失败不保留旧值**。`Fetch` 拿到 error 直接向上抛，不会回退到已过期的旧数据。

## 业务用例：怎么选

下面几个例子不展开业务逻辑，只看选型的判断依据。

### 一个面板的全部排序位次

面板下发要知道某面板下每个二级分类里物料的排列顺序。键是面板 id，值是这份排序结果。

选 `ObjectCache`。理由不是"数据小"，而是**键空间封闭**：面板 id 是有限集合，加载时可以把每个面板的排序一次性算出来装进一个对象。下发请求命中率接近 100%，且 getter 只有在刷新时才跑。

### 某种类型的全部组件

贴纸、滤镜、字体这类组件按类型缓存，键是物料类型，值是该类型全部物料组成的名字字典与 id 字典，并且依赖已填充完毕。

选 `ObjectCache`，同样因为键空间封闭——物料类型是常量枚举。一次加载就把整类组件变成两个 map，之后任何按名字或按 id 的查询都是一次 map 查找。

代价是这类缓存的 getter 很重：查全表、查依赖、逐个填充。所以它的 TTL 不能太短，重载期间读请求会阻塞。

### 单个模板

模板是反例。模板 id 和名字都是开放集合，且单个模板的填充很重——要展开转场、特效、滤镜、字体、音效等全部依赖。全量装进一个对象既不现实也没必要，用户一次只看一个模板。

选 `KVCache`。未命中时单飞保证同一个模板的并发请求只回源一次，不同模板之间互不影响。TTL 由 getter 每次返回，可以比组件缓存长一个数量级，因为代价只由冷启动的那一次请求承担。

### 外部的歌曲与天气

QQ 音乐歌曲、视频号推荐歌曲、天气，回源都是外部 RPC 而不是数据库。

选 `KVCache`。这里的考量不是内存而是**失败语义**：外部调用会失败、会超时，按单键缓存可以让一次失败只影响一个 key，其余请求照常命中。天气的 getter 里还显式处理了"查不到"的情况——返回空结果也照样写入缓存，下次不再打外部接口。

这类缓存的条数上限给得比较小（天气 500 条），因为外部数据的键空间远大于本地数据，命中率天然低，缓存更多只是占内存。

### 权限表

权限是全量配置：staff × module 的映射加管理员名单，一次加载全部行。

选 `ObjectCache`，并且是少数几个**构造后立即 `Reload` 一次**的实例——权限是启动就必须就绪的数据，不能等第一个请求来触发懒加载。

### 用不了 ObjectCache 的地方

有几处业务代码没走 `Fetch`，而是自己 `Get` + 判空 + 批量回源 + `Set`，比如批量取歌曲。形态上就是把 `MultiFetch` 的逻辑手写在业务里：收集未命中的 id，一次批量查回，逐个写回。

结果是这些地方拿不到单飞保护。相同 id 的并发未命中会重复回源，只是批量接口本身成本低，重复几次可以接受。这属于 `KVCache` 的批量路径没被统一使用，而不是刻意设计。

## 设计与取舍

**选型依据是键空间，不是数据量。** 能一次装进来的用 `ObjectCache`，装不进来的用 `KVCache`。判断标准与数据大小无关——一个 5000 条的全量字典照样用 `ObjectCache`，一个只有几百条但键空间开放的外部查询照样用 `KVCache`。

**失败语义两者相反，且都是有意的。** `ObjectCache` 重载失败保留旧值，因为整对象被清空意味着所有请求集体回源；`KVCache` 回源失败直接报错，因为按 key 缓存时旧值已过期，返回它比报错更危险。选错语义会得到两种相反的故障形态。

**`ObjectCache` 的重载会阻塞读。** 整对象替换与 check-lock-check 共用一把锁，getter 慢的时候读请求会等。所以 `ObjectCache` 的 getter 必须快，重活应该放在 `KVCache` 侧或提前算好。

**TTL 抖动是实例级的，不是 TTL 级的。** 每个缓存实例在构造时给 TTL 加一段随机值，而不是每次读随机。这让同一份缓存在一个实例上的过期时间是固定的，实例之间则散开。

## 后续优化方向

**批量路径没有统一。** 几处业务手写了 `Get` + 批量回源 + `Set`，绕过了 `MultiFetch`，也就绕过了统一的上报。收敛到 `MultiFetch` 可以少一套重复逻辑，代价是这些对象要实现 `Item` 接口。

**`ObjectCache` 的 getter 耗时没有上限保护。** 重 getter 期间读请求阻塞在锁上，慢查询会直接放大成请求堆积。可以改成双缓冲——新值在旁路构建完成后再原子切换。

**`KVCache` 的容量参数是经验取值。** 32 桶、5000 到 10000 条、淘汰 16 到 128 条，各处基本一致，没有按实际键空间和命中率校准过。上报里已有耗时与错误，缺的是命中率。

**单飞只覆盖同 key，跨 key 无保护。** 冷启动或批量失效时，不同 key 的并发未命中会同时打到数据库。当前靠 TTL 抖动和刷新时的随机延时间接缓解，不是显式限流。
