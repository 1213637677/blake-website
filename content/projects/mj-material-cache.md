## 要解决的问题

素材系统的读写比极端倾斜：每天被拉取千万次，运营可能一天只发布几次。所以读路径必须极快。

但这里有个陷阱——**运营发布一次，如果几百台机器同时收到通知去回源数据库，数据库会被瞬间打垮**。缓存加速的同时必须防止这种失控。

## 实现方案

![缓存刷新合并](/diagrams/07-cache-refresh.svg)
*缓存刷新合并*

### 进程内缓存为主

几乎所有读路径都是：进程内缓存命中就返回，不命中才回源数据库。

两类缓存分工：

| 类型 | 用途 | 特点 |
|---|---|---|
| 对象缓存 | 全量模板、配置、推荐索引 | 一次加载整批数据 |
| 分片键值缓存 | 单个素材 | 分桶管理，避免全局锁竞争 |

**过期时间带随机抖动**。比如基础 24 小时，再加一个 0 到 30 分钟的随机值。

原因是如果所有实例同时加载、同时过期，它们会在同一时刻集体回源——这就是缓存雪崩。加了抖动，过期时间就散开了。

### 刷新要广播，但必须合并

运营改了数据，怎么让几百台机器知道？用 Redis 的发布订阅广播一条"某缓存需要刷新"的消息。

但如果每台收到就直接刷新，就回到了开头的问题。解法是**等待队列合并**：

```
实例收到刷新消息
      ↓
进入等待队列
      ↓
是队首吗？
  ├─ 是 → 真正执行刷新
  └─ 否 → 直接返回，不重复回源
```

只有队首真正干活，其余直接拿到结果。

还有一层保险：**刷新前随机延迟 0 到 30 秒**。即使队列机制的时序出现偏差，随机延迟也能把并发峰削平。这是典型的"两道保险"思路——不依赖单一机制的正确性。

### 空值占位防穿透

查询一个不存在的素材，如果不处理，每次请求都会穿透到数据库。

解法是**给"不存在"也缓存一个占位值**。代码里专门定义了一个"不存在"的状态用于这个目的。更细致的一处是：音乐节拍加载时，如果某首歌已被删除，也会写入一个标记为已删除的占位对象而不是什么都不写。

### 大字段故意不缓存

音乐节拍数据里有个体积很大的基础节拍字段，缓存时**主动置空不缓存**——因为它只在编辑场景用得上，而缓存服务的是下发场景。

这是很实在的内存权衡：只缓存真正会被用到的部分。

## 背景与约束

**读写比极端倾斜**决定了几乎所有设计都向读路径倾斜，写路径可以慢、可以异步。

**部署实例数量多**。这既是需要缓存的原因（分摊读压力），也是需要刷新合并的原因（实例多才有集体回源的风险）。

**运营发布是低频但高影响的操作**。一次发布影响所有用户，所以必须保证发布后的缓存一致性，同时不能让发布动作本身压垮系统。

## 还能怎么优化

**广播消息的可靠性依赖 Redis 发布订阅**。发布订阅是"即发即忘"的，如果某个实例当时网络抖动没收到，它的缓存就会长期停留在旧版本。更稳的做法是加版本号机制——实例定期比对版本号，发现落后就主动刷新，不单纯依赖广播。

**等待队列的分布式实现需要保证只有一个队首**。这类逻辑在并发下容易出问题（比如两个实例都认为自己是队首），应该依赖 Redis 的原子操作而不是应用层判断。

**缓存与数据库的一致性窗口**。当前是发布后广播刷新，中间存在短暂不一致。对素材这类内容可以接受，但如果未来有强一致需求，需要重新设计。

## 补充说明：本模块读不到的部分

- Redis 集群的部署形态与持久化配置不可见，无法评估广播丢失的实际概率
- 各服务的实际实例数量与 QPS 无法从代码确认
- 对象缓存的具体淘汰策略在公共库中实现，细节未完全展开
- 素材检索服务的索引更新机制不可见，因此缓存与检索索引之间的一致性未能验证
