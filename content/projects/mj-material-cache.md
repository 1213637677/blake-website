`mmvsimplelogicsvr` 的读路径全部走进程内缓存：组件、模板、面板、音乐、歌单、运营配置，一共 50 多个缓存实例分布在 28 个文件里。素材系统读写比极端倾斜——下发请求密集，运营一天可能只发布几次——所以读路径几乎不碰数据库，数据库只在缓存未命中或收到刷新消息时被访问。

缓存本身是两层设施：进程内的 `ObjectCache`（整个对象一份）与 `KVCache`（分桶键值 + 单飞），加一层 Redis 广播把运营的发布动作扩散到所有实例。设计的难点不在命中率，而在**几百个实例收到同一条刷新消息时，如何不让它们同时回源**。

## 核心流程

![缓存刷新合并](/diagrams/07-cache-refresh.svg)
*缓存刷新合并*

一次读请求的路径是固定的：进程内缓存命中直接返回，未命中则回源数据库并写回。刷新由三条独立触发源驱动——定时过期、Redis 广播、写操作后的主动失效。

### 两类进程内缓存

`ObjectCache` 存整个对象一份，用 `atomic.Value` 承载，`Get` 时 check-lock-check，未命中才调 getter。它适合一次加载整批数据的场景：全量组件字典、面板排序、运营配置、推荐索引。带 `interval > 0` 时会起一个 goroutine 定时 `Reload`。

`KVCache` 基于 `ccache` 分桶，每个键独立 TTL，`Fetch` 未命中时走 `singleflight` 合并并发回源。它适合按单个键查询的场景：模板 id、模板 name、歌曲片段。参数基本是 32 桶、5000 到 10000 条上限、每次淘汰 16 到 128 条。

分桶是为了避免全局锁竞争，单飞是为了防止同一个键的并发未命中打穿到数据库。批量场景另有 `MultiFetch`，未命中的键一次性查回，不走单飞。

### 组件缓存：字典与面板分离

组件（贴纸、滤镜、特效、字体、转场等）按类型建两套缓存，分离的依据是访问模式不同：

| 缓存 | 键 | 内容 | 规模 |
|---|---|---|---|
| `DictCaches` | 物料类型（60 种） | name/id → 物料实体，含依赖填充结果 | 每类一份全量 |
| `SortedCaches` | 面板 id（139 个） | 面板与二级分类下的排序位次 | 每面板一份 |

`DictCaches` 一次把某类型所有线上物料加载成 name/id 两个字典，并且**线上与待验收两份同时构建**：先查线上状态，深拷贝出一份再填入草稿版本，用四个字典分开存。运营在管理后台预览的是待验收版本，用户拿到的是线上版本，两者共用一次加载。

`SortedCaches` 只存排序位次，不存物料实体——面板下发时先取位次，再按位次去 `DictCaches` 里取实体。这样物料内容更新只需要刷字典缓存，面板顺序调整只需要刷排序缓存。

两类缓存的 TTL 都是 15 分钟加 0 到 60 秒随机。

### 模板缓存：索引与实体两级

模板是最重的缓存对象——一个模板要展开出转场、特效、滤镜、字体、音效等全部依赖。所以拆成两级：

```text
templateNameIdKVCache   name -> templateId        // 索引，10000 条
templateIdKVCache       id   -> 填充后的模板实体   // 实体，5000 条
```

按 name 查询先命中索引层拿到 id，再查实体层。同一模板被多次请求时索引层几乎必然命中，只有实体层可能未命中；模板改名或下线时只需要失效索引层的一个键。

实体层的回源是重活：查模板记录 → 查全部依赖名 → 一次查回所有依赖物料 → 按类型填充。系统另有一张预填充表，命中时直接返回，失败才回落到实时填充，并同时告警。

TTL 是 2 小时加 0 到 30 分钟随机，比组件缓存长一个数量级——模板填充成本高，值得用更长的不一致窗口去换。

模板另有 `templateExtraCache`（1 小时 TTL）存全局贴纸名单和歌单到模板的映射，避免每次请求重新遍历全部模板。

### 音乐缓存

歌曲片段和歌单走 `KVCache`，TTL 1 小时加 0 到 120 秒随机；歌单面板、场景面板走 `ObjectCache`，15 分钟。音乐节拍单独一份 `KVCache`，15 分钟 TTL。

音乐节拍有两个刻意的例外。一是**已删除的歌曲写入占位对象**而不是什么都不写——占位对象带删除状态，读路径据此判断"有记录但已删除"，避免每次都回源。二是**基础节拍字段在缓存前主动置空**，这个字段体积大且只在编辑场景用得上，下发场景用不到，缓存它只是白占内存。

### 刷新：广播、合并与抖动

运营发布后，写路径调用 `ReloadObjCache` 向 Redis 频道广播一条消息，消息体是 `{Type, CacheName}`，区分对象缓存与键值缓存两类。所有实例订阅同一个频道，按 `CacheName` 找到本地对应的缓存实例执行 `Reload`。

键值缓存的刷新语义不同：消息带具体 key，收到后直接 `Delete`，下次读自然回源。这是惰性刷新——广播只负责让缓存失效，不承担加载成本。

三层机制共同防止集体回源：

**等待队列合并**解决单个实例内的重复刷新。同一个缓存在短时间内收到多条刷新消息时，每条消息创建一个代表自己的 reloader 挂到等待队列；队首直接执行刷新，其余阻塞等待。刷新完成后，队列中排在队首之前的全部被标记完成并唤醒，最后一个被唤醒的负责下一次写入。

这个队列是**进程内的**，作用是消除单个实例上消息重复触发的重复加载，不是跨实例选主。跨实例的削峰靠另外两层。

**随机延迟**削平跨实例的并发峰。带 `OptRandomDelay` 注册的钩子在真正 `Reload` 前随机睡眠 0 到 30 秒。几百个实例收到同一条广播，睡眠时长不同，回源时间自然散开。

**TTL 抖动**防止周期性集体过期。所有缓存的 TTL 都加了一段随机值，实例之间不会在同一时刻集体失效。

模板缓存没有走通用钩子，而是单独注册了一个订阅：因为模板缓存的加载有先后顺序，且它采用**按 key 删除 + 随机延时**而不是整对象重载。收到消息后先按 id 列表（或一个特殊 payload 表示全量）查回受影响的模板，再对每个模板起一个 goroutine，随机睡眠「模板数 × 10」毫秒内的某个值后删除对应键。批量发布时刷新动作被摊开在一个时间窗内。

### 依赖驱动的级联刷新

组件之间存在依赖：贴纸引用音效，滤镜引用特效，套件引用转场。刷新一种类型必须连带刷新引用它的类型，否则缓存里会出现新旧混合的组件。

级联关系是一张显式的映射表：改音效要连带刷新多种贴纸与特效，改贴纸要连带刷新贴纸面板，改套件要连带刷新五类套件列表。`ReloadMaterialTypeCache` 展开这张表后逐个发广播，改一个底层组件可能触发十几条刷新消息。

这张表是手工维护的。依赖类型新增时如果忘记登记，缓存就会静默地停留在旧版本直到 TTL 到期——这是当前设计里最容易出错的一处。

### 空值占位与穿透

查询一个不存在的对象时，如果不写入任何东西，每次请求都会穿透到数据库。读路径统一处理：查不到就写入一个带"不存在"状态的占位对象，并赋予正常 TTL。

模板实体层同样如此：模板不存在、不是线上状态、或类型不是模板时，返回一个正常的 TTL 而不写入值，未命中状态本身被缓存住。

### 可观测性

所有 getter 都被包装成带上报的版本，`ObjectCache` 与 `KVCache` 各一个包装函数，把函数名、耗时、Pod 名、错误上报到日志服务，缓存名在 `appcontext` 里集中定义为常量。回源耗时与失败因此在监控上可见，这也是判断"某类缓存是否加载过重"的依据。

## 设计与取舍

**组件与面板分离，模板索引与实体分离。** 两次拆分依据相同：把"变化频率低、体积小"的和"变化频率高、体积大"的拆开，让局部更新只失效局部缓存。代价是读路径多一次查表，且两级之间可能出现短暂不一致——索引层指向一个刚被删除的实体，此时读到空值。

**刷新用删除而不是重载。** 键值缓存广播的是失效指令而非新数据，加载成本由下一次读请求承担，且天然被单飞合并。代价是刷新后的第一个请求会变慢，且消息丢失的影响是"读到旧数据"而非"读不到数据"。

**一致性窗口靠 TTL 兜底，不靠广播的可靠性。** Redis 发布订阅是即发即忘，某个实例网络抖动没收到消息时，它的缓存会停留在旧版本直到 TTL 到期。组件缓存 15 分钟、模板 2 小时，就是可接受的不一致上界。代价是运营发布后的生效时间不确定，最坏情况下要等一个 TTL。

**待验收与线上数据共存在一份缓存里。** 运营预览走待验收字典，用户请求走线上字典，一次加载同时构建。省掉了第二套缓存和第二次回源，代价是每份缓存的内存占用翻倍，且预览路径与主路径共用同一把锁。

**大字段与低频字段不进缓存。** 基础节拍字段在缓存前置空，只保留下发场景需要的部分。内存是这套设计的硬约束——单实例要同时容纳 60 类组件字典、139 个面板和上千个模板实体。

## 后续优化方向

**依赖级联表手工维护。** 新增依赖类型时漏登记不会报错，只会让缓存静默停在旧版本直到 TTL 到期。可以从物料关系表自动生成这张映射，而不是维护常量列表。

**广播丢失没有补偿。** 实例错过消息后只能等 TTL。可以引入版本号：写路径更新一个全局版本号，实例定期比对，发现落后主动刷新，把最坏生效时间从 TTL 收敛到检查周期。

**等待队列只覆盖单个实例。** 跨实例削峰目前完全依赖随机延迟的统计特性，实例规模继续增长时 0 到 30 秒的窗口可能不够用。

**刷新失败只记录日志。** 回源失败时 `Reload` 返回错误被记下，缓存保持旧值，没有重试。对模板这类重对象，一次失败意味着该实例要等下一个 TTL 才恢复。

**预加载范围靠配置项圈定。** 模板 KV 预加载只处理"在模板库且打了标签"与"空白/无模板"两类，其余模板靠首次请求冷启动，冷启动的第一次回源在发布后可能集中出现。

## 外部依赖与系统边界

- **Redis 发布订阅承担全部跨实例通知**，其可靠性、部署形态与持久化配置由基础设施决定，消息丢失的实际概率无法从本仓库评估
- **实例数量与 QPS 由部署环境决定**，代码里只能看到防雪崩的机制，看不到削峰参数的实际效果
- **`ccache` 的淘汰策略与 `singleflight` 的语义由公共库实现**，分桶数、上限、淘汰条数是经验取值，未做容量校准
- **模板预填充表由独立的离线流程产出**，其更新频率与行数据完整性决定了实体层命中率，表数据缺失时会静默回落到实时填充
- **素材检索服务的索引更新不在本仓库**，面板缓存与检索索引之间的一致性未经验证
