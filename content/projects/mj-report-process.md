秒剪客户端会把用户的编辑行为上报到数据平台，用于后续的数据分析。上报之前有一道加工环节：补上地理位置（经纬度转国家省市）、给素材打上内容标签（识别画面里是什么）。

`mmvreportprocesssvr` 专门做这件事。它不面向用户、不监听业务端口，是一个纯消费型服务：从消息队列取任务、加工、调用上报服务投递。

## 核心流程

### 为什么独立成一个服务

加工逻辑原本放在在线的检索服务里，用本地队列（dque）消费。拆出来的原因很具体：本地队列是单机的，3 台机器各自堆积，A 机积压时 B、C 空闲也无法分担；加工能力绑在在线服务的部署规格上，无法独立扩缩容；ffmpeg 抽帧和大文件下载这类重操作与在线搜索混跑，拖慢搜索的 P99。

换成 Pulsar 的 Shared 订阅后，同一订阅下的多实例由 broker 自动分摊消息，加实例就是加吞吐。

一个容易混淆的点：**这个改动解决的是"能否弹性扩容"，不是吞吐瓶颈本身**。打标的耗时九成以上花在等大模型返回，如果模型侧容量不足，扩容消费者只是把排队从本服务转移到模型侧。所以判断能否加并发的指标是模型失败率，而不是本服务的队列长度。

### 一次任务的加工步骤

```text
1. 收集素材经纬度 → 批量查 LBS 转国家省市（带缓存）
2. 逐素材打标：COS 下载 → ffmpeg 抽帧/转码 → 大模型 → schema 校验 → base64
3. 构造 1 条 project + N 条 segment 的上报内容
4. 合并成一条批量消息上报
```

地理位置查询是批量的，且结果进缓存——同一片区域的坐标会重复出现，逐个查会浪费调用。

打标只对视频和图片做，其余素材类型跳过。抽帧时间点由 ffmpeg 从文件里探测出的真实时长算出，不用上报数据里带的时长——后者是用户原始素材的时长，与 COS 上存的处理后文件没有对应关系，用它算会全部越过文件末尾、一帧都抽不出来。

### 失败语义分层

这是这个服务最值得看的设计。不同环节失败的处理方式不同，依据是**重投有没有意义**：

| 环节 | 处理 | 依据 |
|---|---|---|
| 消息格式非法 | 确认丢弃 | 重投也不会成功 |
| 加工开关关闭 | 确认丢弃 | 明确不需要处理 |
| 地理位置查询失败 | 容忍，字段留空 | 不影响其他字段的价值 |
| 打标失败 | 容忍，标签留空 | 同上 |
| 上报失败 | 重新投递（延迟 30 秒） | 可恢复的下游故障 |
| 处理过程 panic | 重新投递 | 避免消息静默丢失 |

判据是"这一次失败，重来一次会不会不一样"。数据加工的目的是让上报数据更丰富，某个字段拿不到不应该让整条记录丢失——所以富化类失败全部容忍，只有最终投递失败才重投。

构造上报内容时也有分层：project 级构造失败则整个任务不上报，segment 级失败只跳过那一条。

### tag 要做 base64 编码

打标结果是 JSON，里面含逗号。数据平台按逗号分隔字段，明文上报会被截断导致列错位。所以校验通过后再做一次 base64。

代价是下游消费方必须解码才能用。日志里打印的是编码前的明文，便于排查。

### 背压与优雅退出

消费端是 worker 池，worker 全忙时不再拉取新消息，形成背压。这比无限制地拉消息进来堆积在内存里可控。

收到退出信号后停止拉新消息、等待在途任务完成，未确认的消息由 broker 重投给其他实例。等待时长设为 240 秒，对应单素材加工最长 3 分钟。

### 灰度切换路径

从在线服务的本地队列切到独立服务分四步，每步都可回滚：

| 阶段 | 在线服务 | 本服务 | 目的 |
|---|---|---|---|
| 1 | 本地处理 | 不部署 | 基线 |
| 2 | 双写：本地处理 + 投递队列 | 部署但关闭 | 验证投递链路，不产生重复上报 |
| 3 | 仅投递队列 | 开启 | 正式切换 |
| 4 | 移除本地代码 | — | 清理 |

阶段 2 的"双写但本服务关闭"是关键：投递链路可以被验证而不影响线上数据。出问题回滚只需把开关改回去。

## 设计与取舍

**富化失败容忍，投递失败重投。** 判断标准是重投能否改变结果。这让数据平台拿到的是"部分字段缺失的记录"而不是"没有记录"——对数据分析而言，前者通常更有价值。

**共享订阅换弹性，但不承诺吞吐。** 换 Pulsar 之后加实例就能加消费能力，这是真实的改进。但端到端吞吐的天花板在大模型侧，扩容本服务只是让排队发生在更合适的位置。这个区别必须讲清楚，否则会误判扩容的效果。

**时长必须探测而不是读取上报值。** 上报的元数据和实际文件是两个来源，不对应。代价是每次打标都要跑一次 ffprobe，但读本地元数据是毫秒级，相比秒级的大模型调用可以忽略。

**背压靠阻塞而非限流。** worker 池满了就不再拉消息，让消息留在 broker 上。好处是内存可控、积压可观测（通过端到端延迟指标）；代价是 broker 侧需要正确配置确认超时，否则会重复投递。

**标签编码上报，把复杂度推给下游。** base64 解决了字段截断，但要求消费方解码。这是在数据平台的分隔规则不可改的前提下做的妥协。

## 后续优化方向

**大模型是真正的瓶颈，本服务无法解决。** 打标耗时主要花在等模型，模型容量不足时扩容消费者无效。需要模型侧扩容或对打标做抽样降级。

**确认超时依赖 broker 侧配置。** 客户端没有暴露该配置，需要保证 topic 的确认超时大于单任务最长耗时，否则会重复投递——重复只会导致重复上报，不会造成数据错误，但会放大下游压力。

**部分格式抽帧失败。** HEIC 等格式的抽帧失败被单独计数，说明这是已知问题，但没有针对性的处理或降级。

**临时文件的磁盘占用与并发正相关。** 峰值约等于并发数乘以单素材大小，部署时要确认临时目录容量；当前没有用量监控，只有容量规划建议。

**缓存只覆盖地理位置，不覆盖打标结果。** 同一素材被多次上报时会重复走一遍下载、抽帧、打标的全流程，成本没有被缓存抵消。

## 外部依赖与系统边界

- **任务由在线检索服务投递**，消息契约在两边各有一份定义，改动需保证兼容，契约演进是跨服务的协调成本
- **地理位置转换由 LBS 服务提供**，其覆盖率决定了地理字段的完整度，失败时该字段留空
- **素材文件存放在对象存储**，下载失败即打标失败，下载的耗时与成功率直接影响加工吞吐
- **内容打标由大模型完成**，其容量、耗时与失败率是本服务的实际吞吐上限，本服务的并发参数无法突破这个限制
- **最终上报由数据通道服务完成**，其可用性决定了是否需要重投，本服务不感知数据平台侧的消费情况
