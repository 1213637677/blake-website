`mmvopenlogicsvr` 是秒剪对外的 HTTP 出入口。它自己不持有业务逻辑，把请求转给内部服务，但**鉴权、限频、协议转换都发生在这一层**。

服务上挂了三类接口，鉴权方式各不相同：微信开放平台与公众平台的回调走签名校验；`/nmj/cli/*` 是给命令行工具用的，走 API Key；`/creator/template/api` 是模板创作者后台，走 JWT。此外还有一批不需要鉴权的静态资源与下载页。

这个服务同时承担了内部网页的托管：官网首页、隐私协议、落地页、下载包都从这里出，另有一路反向代理把请求转到内部的 JupyterLab。

## 核心流程

### 三类鉴权并存

| 接口前缀 | 使用方 | 鉴权方式 |
|---|---|---|
| `/open/api` | 微信开放平台、公众平台 | 回调签名校验 |
| `/nmj/cli/*` | 命令行工具 | API Key，缺失时降级到 JWT |
| `/creator/template/api` | 模板创作者后台 | JWT + 元数据加载 |

并存的原因是迁移不能一刀切：命令行工具先于 API Key 存在，早期用 JWT 令牌，新版本改用 API Key。中间件里的处理是**先试 API Key，取不到再降级到旧的 JWT 验证**，两条路径复用同一段校验逻辑。

这样老客户端不会在切换当天全部失效，代价是中间件要同时理解两种凭证，且"没有凭证"和"凭证无效"的返回需要区分清楚。

### API Key 的生成与校验

Key 的格式是 `nmj_` 加 64 位十六进制串，随机部分取 32 字节。

生成时同时产出三样东西，各有用途：

```text
plainText = "nmj_" + hex(randomBytes)              // 只在生成时返回一次
hash      = sha256(plainText)                       // 入库，用于校验
encrypted = aes_gcm(plainText)                      // 入库，用于再次下发明文
prefix    = "nmj_" + hex[:8]                        // 入库，用于列表展示
```

库里存的是哈希而不是明文——这意味着**服务端无法在事后找回某个 Key 的明文**。用户重新登录时要看到明文，只能靠那一列 AES-GCM 密文解出来。所以加密不是为了防数据库泄露后 Key 仍不可用，而是为了让"再次下发明文"这件事成为可能；防泄露由哈希承担。

校验路径是：格式校验 → 算哈希 → 查 Redis 缓存 → 未命中查库 → 回写缓存。缓存 5 分钟，命中后异步更新 `last_used_at`，这个更新失败不影响鉴权结果。

重置 Key 时显式清掉缓存。否则旧 Key 的哈希还在缓存里，重置后 5 分钟内仍能通过校验。

### 微信扫码登录与首次发 Key

命令行工具没有账号体系，用微信扫码换身份：

```text
用户扫码 → 微信 code → 换 access_token + unionId
       → 查该 unionId 是否已有活跃 Key
          ├─ 没有 → 生成 Key，返回明文，标记 isNewUser
          └─ 有   → 解密已有 Key，返回全部明文
```

首次登录自动生成一把名为 `default` 的 Key，用户不需要先申请。这个设计把"注册"和"登录"合成了一个动作——对命令行工具来说，扫码之后立刻拿到能用的凭证，比先注册再领 Key 顺畅。

重置 Key 需要重新扫码：用微信 code 再验一次身份，而不是拿着旧 Key 就能换新的。旧 Key 被吊销、新 Key 的明文当场返回。

### JWT 的三套密钥

JWT 相关的常量里有三套密钥和两组过期时间，分别服务不同链路：

| 用途 | 过期时间 |
|---|---|
| 创作者后台令牌 | 7 天 |
| 命令行令牌 | 7 天 |
| 秒剪客户端令牌 | 365 天 |

解析时按 claims 里的 `Subject` 选密钥：`mjToken` 用秒剪的密钥，其余用创作者密钥。这样一套 `ParseToken` 能同时处理两种签发方，代价是密钥选择逻辑藏在解析回调里，新增签发方要改这里。

Cookie 里的用户标识是加密的，不是明文 `unionId`。令牌里带的是密文，拿出来还要解一次。

### 限频只覆盖个别接口

限频是基于 Redis 的 IP 计数器，实现很直接：`Incr` 拿到计数，计数为 1 时设过期时间，超过阈值返回 429。

值得注意的是它**没有全局启用**，只挂在上传签名这一个接口上（每分钟 100 次）。其余接口不设限频——这个服务的主要流量来自自家客户端与有限的命令行用户，逐个接口配限频的收益不明显。

Redis 不可用时限频直接放行：拿不到计数就 `c.Next()`，不因为限频组件故障而拒绝所有请求。这是"可用性优先于限流准确性"的取舍。

## 设计与取舍

**鉴权在网关层统一做，业务层不重复。** 三类接口的校验都在中间件里完成，controller 从 context 里取身份。好处是业务代码不需要关心凭证种类；代价是中间件要知道所有凭证形态，新增凭证类型时要改中间件而不是各接口。

**Key 明文只在两处出现：生成时和再次登录时。** 库里存哈希与密文，前者防泄露、后者支持再次下发。代价是这套机制同时依赖两个密钥——哈希是单向的不需要密钥，但 AES-GCM 的密钥一旦丢失，所有已存在的 Key 都无法再下发明文，只能全部重置。

**老凭证走降级而不是强制切换。** API Key 中间件在取不到 Key 时回落 JWT，让新旧客户端共用同一批路由。代价是中间件里并存两条验证路径，且"两种凭证都无效"时的错误信息要能覆盖两种情况。

**限频是点状的，不是面状的。** 只对上传签名这类容易被脚本刷的接口设限，其余不设。代价是防护覆盖不全——如果某个未限频的接口被刷，没有任何服务端侧的闸门。

**静态资源与业务接口同进程。** 官网、隐私协议、下载页、落地页都由这个服务托管，还反向代理到 JupyterLab。好处是少一个部署单元；代价是静态流量的可用性问题和接口绑在一起，且反向代理把内部服务暴露在了同一个入口之后。

## 后续优化方向

**三套 JWT 密钥硬编码在源码里。** 密钥轮换需要改代码重新发版，且旧令牌在轮换瞬间全部失效。应当移到配置系统并支持多版本密钥并存。

**限频只覆盖一个接口。** 其余接口完全没有服务端侧的频率约束，防护依赖上游网关或网络层。至少应对写操作（提交任务、上传签名、重置 Key）统一加限频。

**限频用 IP 而非身份。** 命令行工具已有 `unionId`，按身份限频比按 IP 更准确——同一出口 IP 下可能有多个用户，反之一个用户换网络就能绕过。

**`last_used_at` 的异步更新失败被忽略。** 更新失败只影响审计字段，不影响鉴权，但也没有重试或补写，审计数据的完整性没有保障。

**API Key 缓存与重置之间依赖显式失效。** 重置时手动删缓存，如果将来新增了别的 Key 状态变更路径（如吊销、过期），漏掉清缓存就会让已失效的 Key 在 5 分钟内仍可用。

## 外部依赖与系统边界

- **微信开放平台提供扫码登录的凭证兑换**，`code` 换 `unionId` 的可用性与频率限制由微信侧决定，本服务只做一次调用并校验结果非空
- **命令行工具与创作者后台由不同团队维护**，凭证形态的演进受客户端发版节奏约束，这也是新老凭证必须并存的原因
- **内部业务能力由 `mmvsimplelogicsvr` 等下游服务提供**，本服务只做鉴权与转发，接口的实际语义与可用性由下游决定
- **反向代理的 JupyterLab 是内部服务**，其可用性不纳入本服务的健康检查，代理失败的表现由被代理方决定
- **Redis 同时承担限频计数与 Key 缓存**，不可用时两者都退化为放行或回源，降级行为是显式的但会丢失该时段的统计
