秒剪管理后台的数据（素材、模板、版本、面板、权限）过去只能靠后台页面查。要让智能体能用自然语言问"某个素材的当前线上版本是什么"，需要一个能被智能体调用的接口。

`mmvmanagemcpsvr` 就是这个接口。它实现 MCP 协议，暴露一组只读工具，智能体通过它查询管理后台的数据。

服务本身不持有数据、不实现查询逻辑，只做三件事：**协议转换、身份校验、参数收敛**。真正的查询全部转发给上游的素材管理服务。

## 核心流程

### 为什么要独立成服务

上游的素材管理接口走内部 mesh 通道，请求体与回包都是 protobuf 封装，外部 MCP 客户端无法直接对接。与其改造上游（会影响所有现有调用方），不如在外面加一层 JSON 网关。

独立出来的收益是上游只需要新增一个普通 JSON 入口，协议适配、身份校验、工具定义都收在新服务里。代价是多一个部署单元和一次网络跳转。

### 两种传输方式

MCP 有两种传输，服务都支持：

| 路径 | 方式 | 用途 |
|---|---|---|
| `POST /mcp` | Streamable HTTP | 单条或批量 JSON-RPC，一次请求一次响应 |
| `GET /mcp/sse` + `POST /mcp/message` | HTTP+SSE | 建立长连接，结果按 sessionId 经 SSE 流下发 |

Streamable HTTP 一次 POST 可以带一条或一批 JSON-RPC 消息：请求体以 `[` 开头就按批量解析，否则按单条。全部是通知（无需响应）时按协议回 202，不返回响应体。

SSE 模式需要维护会话表。会话是**进程内的**，多实例部署时由接入层按 sessionId 做会话保持——这是一个明确的部署约束，不是可以随意扩容的无状态服务。会话有闲置回收，避免长连接堆积。

### 身份走太湖令牌

用户身份通过太湖个人访问令牌传递：智能体平台把令牌放在请求头里透传，本服务调用太湖的 introspect 接口校验令牌真实性，拿到 `staffName` 与 `staffId`，结果缓存 5 分钟避免重复调用。

校验通过后身份放进自定义请求头透传给上游，由上游按原有的权限基线做校验。**本服务不做权限判断**——哪些人能看哪些数据，仍然由上游的 RBAC 决定。这样权限规则只有一处，不会因为加了 MCP 入口而产生第二套权限逻辑。

### 工具即上游接口的映射

每个工具对应上游的一个已有能力：

| 工具 | 能力 |
|---|---|
| `material.list` / `material.search` | 素材列表与搜索 |
| `material.batch_get_by_id` / `batch_get_by_name` | 批量取素材 |
| `panel.display_list` / `panel.list_subtypes` | 面板与子分类 |
| `version.list_drafts` / `version.get` / `version.get_product` | 版本查询 |
| `permission.get_self` | 查自己的权限 |
| `sql.query` | SQL 查询物料表 |

全部只读，写接口不注册——**不注册即不可达**，这是最直接的写防护。

工具用 `init()` 里的注册表模式声明，声明内容包含名称、描述、输入 schema。描述写得比普通 API 文档细，因为它同时是给模型看的提示词：SQL 工具的描述里直接写了可用表名、字段、JSON 嵌套字段怎么提取、不要在 SQL 里写 LIMIT。

### 参数收敛：夹紧而不是报错

所有批量参数都被夹紧到上限，而不是超限报错：

```text
列表长度：未传用默认 20，超过 100 夹到 100
批量 ID：超过 100 截断到前 100
批量名称：超过 100 截断到前 100
SQL limit：未传用 100，超过 500 夹到 500
```

夹紧之后**重新序列化再发给上游**，保证上游收到的永远是收敛过的参数。这个细节的意义是：上游不必再各自实现一遍长度校验，且夹紧逻辑集中在网关一处。

对智能体来说，超限被夹紧比报错更有用——它想要"前 200 条"，拿到前 100 条仍然能继续，拿到一个错误就只能停止。

### SQL 工具的安全边界

SQL 工具允许智能体写 SELECT 查物料表。安全检查**全部在上游实现**：只允许 SELECT、表白名单、强制 LIMIT。本服务只做参数校验与透传。

这个分工是有意的：SQL 执行能力的持有者是上游，安全策略应该跟着能力走，放在网关层会因为两边演进不同步而产生缺口。代价是网关无法独立证明"这个 SQL 是安全的"，只能依赖上游。

分页用 `start` + `limit` 而不是让模型在 SQL 里写 LIMIT/OFFSET。原因是模型写的分页语句容易出错，统一由参数控制更可靠，且便于夹紧。响应里带 `truncated` 与 `nextStart`，告诉模型还有更多数据以及下一页从哪开始。

## 设计与取舍

**协议适配放在外面，不改造上游。** 上游保持 protobuf + mesh 的形态不动，新增一个 JSON 入口即可。代价是多一跳网络和一份需要同步维护的工具定义。

**权限判断不在这里做。** 身份校验在这里，权限校验在上游。好处是权限规则只有一处，不会因为新增入口产生第二套逻辑；代价是网关无法在转发前拒绝越权请求，越权要到上游才被发现。

**工具只读，靠不注册来保证。** 写接口不出现在工具列表里，智能体就调用不到。这比在 handler 里判断方法名更可靠——不可达比"可达但拒绝"更难被绕过。

**超限夹紧而非报错。** 让智能体拿到部分结果继续工作，而不是失败终止。代价是模型可能意识不到结果被截断了，所以响应里必须显式带 `truncated` 标志。

**SQL 安全策略放在上游。** 跟着能力走，避免两边演进不同步。代价是网关层无法独立保证安全，只能信任上游。

**会话在进程内。** SSE 模式的会话不跨实例共享，多实例部署需要接入层做会话保持。这让服务不是纯粹的无状态服务，扩容时要考虑长连接的分布。

## 后续优化方向

**会话不跨实例，扩容受限。** SSE 模式依赖进程内会话表，多实例要靠接入层做会话保持。如果接入层不支持，只能单实例部署或改用 Streamable HTTP。

**工具定义与上游接口需要手工同步。** 工具的输入 schema 是手写的，上游接口变化时这里要跟着改，且没有自动校验——schema 与上游不一致只会在调用时暴露。

**身份缓存 5 分钟内无法感知权限变更。** 令牌校验结果缓存 5 分钟，这期间用户被收回权限后仍能通过本服务查询，实际拦截依赖上游的权限校验。

**夹紧是静默的。** 参数被截断时响应里不一定有明确提示（SQL 工具有 `truncated`，其他工具没有），模型可能误以为拿到了完整结果。

**SQL 工具的可用性依赖上游的白名单维护。** 新增可被查询的表要在上游加白名单，网关侧的 schema 描述也要同步更新，两处不一致会让模型写出被拒绝的 SQL。

## 外部依赖与系统边界

- **太湖提供令牌校验与身份信息**，其可用性决定了所有工具调用的入口能否通过，校验结果缓存 5 分钟
- **上游素材管理服务持有全部数据与查询能力**，本服务只转发，查询的性能与结果语义由上游决定
- **SQL 执行的安全性由上游保证**（只允许 SELECT、表白名单、强制行数上限），本服务不做语句检查
- **智能体平台负责令牌透传与会话路由**，多实例部署时按 sessionId 做会话保持是接入层的责任
- **MCP 协议的实现细节由开源库承担**，两种传输方式的语义与演进受协议版本约束
