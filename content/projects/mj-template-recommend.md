## 要解决的问题

用户选了几段素材打开模板面板，系统要推荐"适合这些素材"的模板。难点在于推荐必须**理解素材内容**——几段海边视频和几段美食视频该推的完全不同。

同时还有两个现实约束：外部排序服务可能不可用；推荐结果必须可控（运营要能干预）。

## 实现方案

![模板推荐主流程](/diagrams/05-recommend-flow.svg)
*模板推荐主流程*

### 第一步：识别"这是什么工程"

素材的标签不由服务端计算，而是**客户端或端上模型算好后随请求带上来**，服务端做聚合。

演进有两代：

| | 早期 | 现在 |
|---|---|---|
| 上送内容 | 浮点特征向量 + 描述数组 | 整数标签索引 + 是否超阈值位 |
| 服务端处理 | 对每个素材取归一化后最大分量 | 计数聚合 |
| 决出工程标签 | 按素材数 → 总时长 → 累加分三级排序 | 同左 + 配置映射 |

从"传向量"到"传索引"是个值得记的变化：向量传输量大、服务端还要做归一化计算；改成索引后传输小、服务端只做计数。同时保留了新版本到旧版本的兼容映射表，老客户端不受影响。

放在端上算的原因是**服务端没有原始视频**，要算就得先上传分析，成本和延迟都不可接受。代价是服务端必须容忍不同客户端版本上来的标签格式差异。

### 分类不是实体，是三元组派生

面板上的一级菜单（旅行、美食等）不是数据库里的一张分类表，而是**三个维度拼出来的缓存键**：适配的视频类型 + 画幅比例 + 横竖方向。

召回索引按这个键组织。好处是新增分类不用改数据结构，改配置就行。

### 四代方案并存

| 版本 | 形态 | 排序来源 |
|---|---|---|
| V2 | 多分类卡片 | 规则 |
| V3 | 收敛为单分类 | 规则 |
| V4 | 单分类 + 分区召回 | 规则 |
| V5 | 单分类 | 外部排序服务 |

入口做分流，决定这次请求走哪一代。

### 主链路（模型排序版）

流程是：请求校验 → 客户端元信息校验 → 加载当前使用模板 → 工程识别 → 方向判定 → 画幅判定 → 构造全局配置 → 算 AI 取段后的段数 → 取用户标识 → 调外部排序服务 → 结果校验 → 三段拼装 → 过滤 → 上报。

几个关键设计：

**用户标识是强依赖**。取不到就直接失败——因为个性化完全依赖它，拿不到就无法给出有意义的个性化结果。

**结果不足就报错而不是返回残缺列表**。少于阈值直接报错触发降级。原则是宁可给用户一个规则版的完整列表，也不给一个模型版的残缺列表。

### 四道防线

把排序外包给模型服务，但业务侧留了四道防线：

**一、入口分流**。游客、关闭个性化的用户、配置关掉开关——这些直接走规则版，根本不调模型服务。

**二、置顶覆盖**。最终列表是分段硬拼的：当前正在用的模板排第一，然后是配置的固定模板、画幅匹配的置顶模板，最后才是排序服务的结果依次填充。**排序服务决定不了最前面几位的样子**。

**三、结果校验**。数量不足就报错降级，见上。

**四、逐条过滤**。排序服务给的是模板 ID，不代表一定能出——还要做全局去重、客户端版本适配过滤、推荐条件过滤。

### 规则版为什么保留

规则版不是简单兜底，它有完整的分区召回结构：

| 区 | 来源 |
|---|---|
| 置顶区 | 运营配置的固定位 |
| 主题推荐区 | 按主题标签命中 |
| 普通区 | 分类固定位 + 池子随机打散 |
| 次画幅兜底区 | 主画幅不够时从反方向补 |

每个模板都**记录自己来自哪个通道**。这个标记让"模型排序 vs 规则排序"的效果归因成为可能——能算清楚某次点击来自哪种召回。

保留规则版有两个理由：它是模型服务出问题时的可靠退路；更重要的是它是**对照组**，没有对照组就无法判断新方案到底好在哪。

## 背景与约束

**为什么标签演进到索引格式**。向量方案在端上算完后还要传一大串浮点数，弱网环境下是负担；索引格式只有几个整数。

**为什么必须保留规则版**。外部排序服务是跨团队依赖，其可用性不在自己掌控内。

**个性化的边界**。用户标识拿不到（游客或权限问题）时，不能假装能做个性化，必须显式走规则版。

## 还能怎么优化

**外部排序服务是个黑盒**。只能看到入参出参，无法分析其召回策略和排序模型。这导致效果归因只能到"用了哪种召回"这一层，无法深入。如果能拿到更细的打分信息，归因会更有价值。

**规则版与模型版的效果对比依赖埋点质量**。当前有召回源标记和降级上报，但长期看应该建立固定的对比实验机制，而不是靠事后分析。

**分区召回的随机打散可能不够优**。普通区用随机打散保证多样性，但没有考虑用户对已展示内容的疲劳度。可以加入曝光过滤。

**标签格式的兼容映射是持续负担**。每加一代标签格式就要维护一份到旧格式的映射，长期看需要收敛。

## 补充说明：本模块读不到的部分

- **外部排序服务的实现不可见**——只能看到请求的字段与返回的结果，其召回策略、排序模型、特征工程均无法分析
- 客户端或端上模型的标签计算逻辑不在本仓库，无法评估其准确率
- 人工标注数据的具体使用方式（如何传给排序服务）未能完全确认
- 模板创建与审核的完整流程在另一个独立仓库，本仓库只有运营侧能力
