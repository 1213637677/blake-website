`mmvtemplatecreatorsvr` 支撑创作者在创作端制作模板：新建、编辑、提交审核、发布到视频号。这条链路和运营在后台配置模板是两条独立的入口——运营侧在素材中台，创作者侧在这个服务，两边最终汇到同一份模板主数据。

服务要解决的核心问题是**一个草稿模板如何走到线上可用**，中间要过初审人员分配、信安过检、性能检测、打包同步等多个环节，且这些环节大多不在本服务内完成。

## 核心流程

### 模板状态机

状态常量有 13 个，分成三组：提交审核前、审核中、发布中。

```text
未提交 → 已提交 → 初审中 → 审核未通过 / 审核通过
                                      ↓
                        发布开始 → 发布完成 / 发布失败
```

另有一组独立的**信安过检状态**与模板状态并行推进：未完成、已通过、未通过、失败。两个维度分开是因为信安过检由外部服务异步完成，其结论不直接等于模板能否发布——模板状态由审核人员推进，信安状态是其中的一个检查项。

发布相关的三个状态（开始/完成/失败）说明发布是异步的：接口只把状态置为"发布开始"并投递消息，真正的打包与同步由消费端完成。

### 提交：绑定校验与初审分流

提交模板前要校验账号已绑定视频号，且绑定关系仍然有效。校验不是查一次库就完事——还要拉一次该用户当前的视频号账号列表，确认绑定的那个账号还在列表里。这一步针对的是运营账号后来被微信侧移除的情况，只查本地绑定记录会放过已失效的关系。

提交后的分流按模板类型和提交者身份决定：

```text
剪辑模板        → 已提交，等待审核
拍摄模板 + 外部创作者 → 初审中，并投递初审人员分配任务
拍摄模板 + 内部员工   → 已提交，跳过初审
```

初审人员分配走消息队列，不在这里同步指定。已被拒绝过的模板重新提交时保留上次的审核人，避免同一模板反复换人审。

提交后另起一个 goroutine 做三项检查：信安过检、模板包大小、性能检测。性能检测只对拍摄模板做，调用外部检测服务拿一个任务 ID 存下来。

### 发布：投递消息而非同步执行

发布接口只做三件事：校验状态允许发布、写回视频号账号信息、投递发布消息。

真正的打包与同步在消费端：秒剪侧更新模板、微信侧打包并同步到模板库。本服务不知道这一步的进展，只能通过状态常量（发布完成/发布失败）间接观察。

这个设计让发布接口很快返回，代价是**发布失败不能同步反馈给用户**，用户看到的是"发布中"，失败要等状态被改回来。

### 两套模板模型的转换

创作者端和运营侧用的是两套不同的数据模型，需要互相转换：

| | 创作者端模型 | 运营侧模型 |
|---|---|---|
| 用途 | 创作端编辑与保存 | 下发与渲染 |
| 结构 | 按创作语义组织 | 按渲染语义组织 |

转换是一个 builder，逐字段搬运：自定义标记点、歌曲配置、背景、剧情线、片头片尾、滤镜、数码变焦、变速等。转换后才能复用运营侧的填充与校验逻辑。

这里的取舍是**不统一模型**：创作端的编辑语义和运营侧的下发语义差别太大，强行统一会让两边都别扭。代价是转换代码要跟着两边的演进同步改，且新增字段要在 builder 里补。

### 制作过程中的时间轴预览

创作者编辑模板时要实时看到剪辑时间轴的效果，这个计算不轻（要展开依赖、填充组件、算时间轴），所以做成异步任务：

```text
提交计算 → 生成 taskId → 起 goroutine 算 → 结果写 Redis（TTL 3 分钟）
查询     → 按 taskId 读 Redis
```

结果键带 3 分钟 TTL，查不到时区分两种情况：Redis 返回空表示"还没算完"，其他错误表示"出错了"。这两种状态返回给客户端的语义不同，前者应该继续轮询。

任务 ID 用 UUID 去掉横线生成，不落库——这个预览结果是一次性的，没有持久化价值。

## 设计与取舍

**审核状态与信安状态并行而非嵌套。** 信安过检由外部服务异步完成，把它做成独立维度而不是模板状态的一个分支，避免了"审核中"和"信安中"两个状态互相等待的组合爆炸。代价是判断"能否发布"时要同时看两个字段。

**提交后的检查全部异步。** 信安、包大小、性能检测都在 goroutine 里跑，提交接口不等它们。好处是创作者提交后立刻得到响应；代价是这些检查失败不会阻止提交，只能事后修正。

**发布是投递消息而非同步执行。** 接口只改状态、发消息，打包同步在消费端。好处是接口轻量、重活可独立扩缩容；代价是发布结果不同步，且本服务无法感知消费端的积压情况。

**初审人员分配走消息队列。** 分配逻辑不在本服务，投递任务让专门的服务去处理。好处是本服务不需要维护审核人员表与分配策略；代价是分配失败时模板会卡在"初审中"没有处理人。

**两套模型靠 builder 转换，不做统一。** 创作语义与下发语义各自保持清晰。代价是转换层成为演进的瓶颈——两边任一侧加字段都要改这里，漏了就静默丢失。

**预览结果存 Redis 不落库。** 一次性的中间结果，3 分钟 TTL 足够。代价是节点重启或 Redis 清空会让正在进行的预览任务丢失，客户端只能重新发起。

## 后续优化方向

**发布失败不同步反馈。** 用户点发布后看到的是"发布中"，失败时没有主动通知，只能刷新后看到状态变回失败。可以增加发布结果的回调或状态变更通知。

**13 个状态常量的合法迁移没有集中校验。** 每个接口各自判断前置状态（比如发布只允许"审核通过"和"发布失败"），新增状态时容易漏改某处判断。应该收敛成一张迁移表。

**转换 builder 需要手工同步。** 创作端与运营侧任一侧新增字段都要在 builder 里补，漏掉不会报错，只会在转换后静默丢失该字段。可以用结构对比或测试覆盖来兜底。

**信安过检与包大小检查的结果没有回写路径。** goroutine 跑完只更新状态，若外部服务不可用则会一直停在"未完成"，没有重试或超时处理。

**初审分配失败无补偿。** 消息投递失败时提交接口直接返回错误，但模板状态已改为"初审中"，会留下没有审核人的模板。

## 外部依赖与系统边界

- **信安过检、性能检测由外部服务完成**，本服务只发起调用并保存任务 ID，其耗时与判定标准决定了模板从提交到可用的时间下限
- **初审人员分配与微信侧打包同步均由消息队列的消费端处理**，消费端在另一个服务，其吞吐决定了发布与初审的实际速度，本服务无法感知积压
- **视频号账号关系由微信侧提供**，绑定关系的有效性要实时拉取校验，本地记录只作为缓存而非依据
- **运营侧的模板模型与填充逻辑在素材中台**，本服务转换后依赖其完成展开与校验，两侧模型演进需同步
- **消息投递依赖 Pulsar**，投递失败时本服务的状态已变更，一致性由消费端的幂等与重试保证
