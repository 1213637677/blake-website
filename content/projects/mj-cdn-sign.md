## 核心流程

素材和模板文件通过 CDN 分发，直接暴露地址会被盗刷。要做防盗链。

难点不在"怎么签名"，而在于**防盗链会破坏另一类链路**：带时间戳的签名 URL 会过期，但有些场景需要的是**长期稳定的地址**。


![CDN 签名与豁免判定](/diagrams/06-cdn-sign.svg)
*CDN 签名与豁免判定*

### 两套签名，不要混淆

| | CDN 防盗链 | 对象存储直传凭证 |
|---|---|---|
| 目的 | 防止盗刷 | 授权客户端直传直下 |
| 谁生成 | 服务端自己算哈希 | 存储服务签发 |
| 时效 | 时间戳参与哈希 | 有效期参数（默认 5 分钟） |
| 时机 | 回包前统一改写响应 | 签发接口直接返回 |

CDN 防盗链的做法是**回包时对整棵响应 JSON 做递归遍历**，把命中的字段值替换成带签名的地址。业务代码完全无感知——签名逻辑集中在一处，不需要每个接口各自处理。

用户上传走的是另一条路：服务端只**签发凭证不中转文件**，客户端直传对象存储，业务服务器完全不承担媒体流量。签发结果还会整体加密后下发，防止凭证被截获复用。

### 核心矛盾与三层调和

这是这个模块真正的设计核心。

**矛盾**：防盗链要求 URL 有时效性；云控配置、构建产物、开放平台要求 URL 有稳定性。

如果全开签名，云控里写入一个会过期的地址，这个配置被长期缓存、跨版本复用、甚至被其他系统读取——就是一颗定时炸弹。所以云控配置里只允许写私有桶路径之外的链接，这条约束是签名开关之外的一道人工闸门。

如果全关签名，防盗链就没意义。

解法是三层判断，而不是二选一：

```
强制开启集合  →  特定接口无论客户端如何都签名
强制豁免集合  →  特定接口无论客户端如何都不签名
版本条件      →  满足条件的客户端才签名
```

豁免清单里每一条的道理不同：

| 豁免对象 | 为什么 |
|---|---|
| 创作者视频相关 | 消费方不是自家客户端，拿不到也不需要鉴权 |
| 发布包相关 | 需要长期稳定可下载 |
| **云控配置** | 配置会被长期缓存和跨版本复用，过期地址是定时炸弹 |
| 构建流水线 | 构建产物需要稳定可下载 |
| 预加载资源 | 同左 |

**版本条件的存在是因为不能一刀切**。老客户端不认识签名地址，直接给它会显示不出来。所以只能逐步推进：新客户端和内部后台先上，老客户端维持原样。这是一个**在线迁移**，不是一次切换。

## 设计与取舍

**CDN 域名在迁移中**。老域名和新域名并存，签名逻辑只对老域名生效，这本身就是迁移期的临时状态。

**客户端版本跨度大**。前面提过，这是全系统的共性约束，在防盗链上体现为"必须按版本灰度"。

**消费方不只一个**。除了自家 App，还有创作者平台、开放平台、构建系统——它们的鉴权能力不同，不能统一要求。

## 后续优化方向

**靠字段名后缀识别 URL 是个妥协**。当前用"字段名以 url 相关后缀结尾"来判断哪些值是 URL，对数组里的 URL 和其他命名方式无能为力——漏签的 URL 不会被报错，只会静默地保持未签名状态。

更好的做法是**让业务层显式声明哪些字段是资源地址**（比如用结构体标签），而不是靠命名约定猜测。改造成本不低，但能根治误判和漏判。

**签名密钥硬编码在服务里**。当前是一个常量。更合理的做法是支持轮换，并放到配置或密钥管理服务里。

**豁免清单靠前缀匹配维护**。随着接口增加，这个清单会持续膨胀，且前缀匹配的表达力有限。可以考虑改成配置项驱动的显式名单。

## 外部依赖与系统边界

- **CDN 侧的鉴权校验由 CDN 完成**，签名算法与校验规则必须与 CDN 配置一致，签名被拒时的降级行为由 CDN 决定
- **对象存储的凭证校验由存储服务完成**，直传凭证的有效期是双方约定的参数，本服务只负责签发
- **客户端对签名地址的兼容程度由客户端版本决定**，只能从灰度条件反推，无法在服务端验证
- **签名密钥的轮换由配置系统管理**，本服务按当前配置签名，不参与密钥的生成与轮换
