用户选几段素材、挑一个模板、选一首歌，服务端一次请求返回整条成片的结构：每个片段从原素材的哪一秒开始、占几个音乐小节、片段之间怎么转场、特效和字幕挂在哪个时间区间上。渲染在客户端完成，服务端交付的是一份**工程描述**。

服务落在 `mmvsimplelogicsvr` 的一个 CGI 上，按 `cmd` 分三种入口：`smartclip` 走完整剪辑，`decorate` 只重新包装不取段，`musictimeline` 单独下发音乐节拍轴。剪辑主流程是纯 CPU 计算，不持有视频文件，只依赖模板缓存、音乐元数据和一个变速曲线计算服务。

## 核心流程

![智能剪辑编排流程](/diagrams/03-smartclip-flow.svg)
*智能剪辑编排流程*

一次请求的处理顺序是固定的：取模板并套用自定义套件 → 标准化请求 → 决定剪辑风格 → 取段 → 按音乐排时间轴 → 填转场 → 应用变速 → 叠加装饰组件 → 输出。差异集中在"决定剪辑风格"和"排时间轴"两步，其余是各风格共用的包装逻辑。

### 剪辑风格的路由

风格有五种常量：`StyleChorusBeat`（一段一小节，卡副歌）、`StyleContrastBeat`（主歌两小节 + 副歌）、`StyleRhythm`（按标记点卡）、`StyleNoClip`（不重新取段）、`StyleDefault`（交给模板决定）。

决议顺序是请求带的 `clipStyle` → 模板的 `DefaultClipStyle` → 按模板适配的视频类型回退到旧规则。旧规则是一层兼容：特定的视频类型对应 `StyleContrastBeat`，活动类模板对应 `StyleRhythm`，其余走 `StyleChorusBeat`。

还有一条优先级更高的分支：请求里带 `displayClipStatus` 时以客户端的展示状态为准，手动调整过的工程强制走 `StyleNoClip`。用户动过手之后再点成片，不该把改动冲掉。

`StyleRhythm` 需要标记点才能成立，来源是模板自带的自定义标记点或歌曲的节奏点。两者都没有时会退化成 `StyleChorusBeat`，硬走会因为算不出槽位而卡不准，宁可降级。

### 时间单位：帧

全程用整数帧作为时间单位，对外下发的毫秒是换算结果。几十个片段的时长累加下来，浮点毫秒的误差会累积成肉眼可见的音画不同步，整数帧不会。

### 节拍槽与副歌校正

卡点的单位是一个节拍槽，长度由 BPM 推出：

```text
slotDurationMs = 60 * 4 / bpm * 1000        // 四分音符、每小节四拍
slotDurationMs = slotDurationMs / bpmCoefficient  // 有修正系数时再除一次
```

副歌起点来自歌曲元数据，主歌起点由它反推：主歌按两小节计，起点就是 `副歌起点 − 2 × 槽时长`。歌曲结构（主歌唱几小节、副歌唱几小节）用 `1+2`、`2+4`、`2+8` 三种编码表示，分别对应主歌 1/2/2 小节、副歌 2/4/8 小节。

副歌起点直接用元数据里的值经常偏高——自动识别会把前奏或过渡段算进去。所以元数据里另有校正点，服务端先判断它可信才用：

```text
// 副歌校正点：不超过 副歌起点 + 1 个槽长 + 10ms 才采纳
correctedChorusBeginMs <= chorusBeginMs + slotDuration + 10  -> 采纳
否则                                                        -> 回退到 chorusBeginMs

// 主歌校正点：落在 [推算主歌起点 ± (1 个槽长 + 10ms)] 内才采纳
minCV <= correctedVerseBeginMs <= maxCV                     -> 采纳
否则                                                        -> 回退到推算值
```

校正点偏早是允许的，这时首段会跨超过一个槽长，观感上是副歌进来前有一个长镜头，属于预期效果。

### 取段：AI 结果只作为建议

素材上带一组 `AiClips`，是端上或客户端模型算好的高光区间。服务端不直接用，先做校正：

1. 起点或终点越出素材总长、时长为零的，丢弃
2. 带表情高光的，子区间必须落在主区间内，否则丢弃
3. 后一片段起点早于当前片段起点的，丢弃当前片段——顺序已经乱了
4. 时长不用 AI 给的，改用**下一个片段的起点减去当前片段的起点**推出；最后一段用素材末尾推出
5. 全部被剔除时回退到等分切

第 4 条是无缝衔接的关键。AI 给的时长彼此可能重叠也可能留空隙，用相邻起点反推则天然保证片段首尾相接、不重叠也不留缝。

没有 `AiClips` 时（旧客户端、或端上没算出结果）走等分切：素材短于 30 秒不切，长于 30 秒则按最长 15 秒逐段切，首段放宽到 30 秒，剩余不足 3 秒的部分并入前一段。图片和实况照片各成一段，不参与切分。

还有一个降级口子：客户端达到 1.9.30、创作类型是回顾活动时，每个素材只取第一段高光。长素材多段展开会让成片节奏拖沓，此时宁可只留一段。

### 槽位分配与片段时长

取段结果只给出"候选区间"，真正决定片段多长的是时间轴。每个片段带一个 `slotLength`（占几个槽，缺省 1），`StyleContrastBeat` 下首段缺省占 2，用来拉开主歌和副歌的节奏差。

`StyleChorusBeat` 与 `StyleContrastBeat` 用等长槽轴，`StyleRhythm` 用标记点之间的间隔作为槽长——标记点不足时先补一个到下一重拍的槽，再按标准槽长补齐。

分配时逐槽累加，如果累加会超过该片段可用的素材长度，就在已凑够至少一个槽的前提下提前收尾，剩下的时长交给变速去消化：

```text
for k < slotLength && nextSlotIdx < len(slots):
    // 已凑够 1 个槽（首段 contrast 要求 2 个）且再加会超出素材可用长度
    if duration + slot.duration > vi.maxOriginClipDuration && k > 0:
        break
    duration += slots[nextSlotIdx].duration
```

槽本身在生成时就做了帧对齐，每个槽的起止都落在与节拍点最接近的帧上，累加出来的工程时长不会出现半帧。

### 二次剪辑与增量下发

用户手动调过之后再触发剪辑，请求里会带上一次输出的 `videoItems`，走二次取段。二次取段不重新切已有片段，只做三件事：修正被用户改坏的边界、剔掉已删除素材上的片段、对新导入的素材做首次取段再插回工程。

修正这一步是必要的：客户端把片段起点拖到素材末尾之后会让可用长度失效，服务端统一夹回素材范围内。用户自己动过起点时，AI 取段结果会被丢弃，可用长度放宽到素材末尾。

切换剪辑方式曾经会触发重新取段，导致段数变化。1.8.20 之后改成取段只在导入素材时发生，切换风格只改排布不动分段。

组件下发同样按增量算。每个组件带生命周期：绑定分段或工程的是 `Template`，绑定音乐的是 `Music`，每次剪辑都重算的是 `Clip`。下发时按"这次剪辑到底改了什么"过滤——换模板或换套件才下发绑定工程的组件，换音乐才下发绑定音乐的组件，绑定分段的只下发尾部新增段上的那几个。绑定音乐节拍的组件用上次剪辑的最后一个节拍下标做断点，工程变长后只补下发延长部分的特效。

### 相对时间轴

模板里的时间点不写绝对毫秒，而是写"相对什么"：工程、第 N 个片段、第 N 个音乐重拍、第 N 个标记点，加上一个偏移量和可选的步长、数量上限。运行时解析成绝对时间。

区间两端不要求锚定同一对象，但不允许两端都不是工程——否则无法解析。非工程轴上的两端还要求步长、上限、参照类型三者一致，避免跨轴组合出无意义的区间。

这层抽象让同一份模板能适配任意长度的素材和音乐："在第 4 个重拍出现转场"不依赖这首歌有多长。模板另有 `DiscardRanges` 表达禁止区，解析完再把落在禁止区内的组件裁掉或丢弃。

### 转场、变速与装饰

转场填在片段之间，数量为段数加一，首尾各留一个空位。交错转场会占用相邻片段的画面时间，所以两侧各预留半个转场时长，并把它加进片段总时长，否则转场会吃掉内容、看起来像跳变。转场时长还要过一道适配检查：超过前后片段中较短者的时长时先减半重试，减半仍超出就放弃这个转场——过长的转场会让卡点失准。

变速分模板曲线变速和用户自定义变速。模板变速下发的是整条工程时间轴上的曲线，按片段边界切分后绑定到各片段，由内部计算服务完成切分和时长换算。切分前会把曲线之间超过 1 秒的空隙补成 1 倍速，避免片段之间速率突变。

卡点剪辑和自由剪辑对变速的期望不同：卡点要维持片段的目标时长（改的是取多少原素材），自由剪辑要维持原素材长度（改的是成片多长）。所以卡点走 `MaintainTarget`，自由剪辑走 `MaintainSrc`。素材不够长时只能慢放，线性速率按 1.0 / 0.75 / 0.5 / 0.25 四档向下取，仍不够才用实际比值。

装饰组件（特效、滤镜、贴纸、字幕、变焦）按相对时间轴解析后叠加，转场、音乐特效、开场片尾、主题装饰四类可以整体替换成套件，同一模板因此能产出不同密度的变体，不用复制多份模板数据。

## 设计与取舍

**节拍是算出来的，不是模型推出来的。** 卡点全程是算术：BPM 推算槽长，槽长累加出工程时长，帧对齐消除误差。模型会引入不确定性，而卡点偏了半拍用户立刻能感觉到。代价是整个计算建立在 BPM 和副歌起点准确的前提上，这两个值标错时数学只会忠实地算出错误结果。

**AI 只在取段环节介入，且结果必须校正。** 视频理解放在端上，服务端不做：端上已经持有原始视频，不需要上传；放进服务端会成为容量瓶颈。代价是服务端拿到的 `AiClips` 不可控，必须做防御性校正，且这些校正只保证区间合法，不保证选段好看。

**服务端只交付描述，不碰渲染。** 分工让服务端不需要关心渲染细节，也支持同一份描述在多端复用。代价是描述必须足够精确，且服务端无法自证描述与渲染结果一致——音画是否同步最终只能在客户端观察。

**帧对齐以锚点为基准向两侧扩散。** 音乐轴上一个节拍点的绝对时间不能变，否则整条轴会漂移；其余点从锚点向前、向后逐点推出，每一点的时长都取整到帧。这样既保住了节拍点，又不会出现半帧。

## 后续优化方向

**BPM 与副歌起点的准确性缺少校验。** 元数据里的 BPM 标错时，卡点会整体错位且没有机制能发现。可以加入结果校验：检查片段时长分布是否异常、首尾片段是否明显偏离槽长整数倍。

**AI 取段的质量问题没有反馈信号。** 现有校正只挡越界和重叠，对"选的片段不好看"无能为力。这类问题需要用户是否重剪、是否手动调整起点作为反馈来驱动优化。

**相对时间轴的表达能力有限。** 目前只能锚定工程、片段、音乐重拍、标记点四类对象，"第一段副歌结束前两拍"这类关系要靠偏移量折算，表达起来仍然别扭。

**版本分支累积。** 请求处理里有 1.6.70、1.6.90、1.7.60、1.8.20、1.9.30 等多处客户端版本判断，分别影响二次取段、自定义变速、变速类型下发、切换风格是否重新取段、是否只取一段高光。这些分支是兼容旧客户端的必要代价，但也让主流程难以一眼读全。

## 外部依赖与系统边界

- **AI 高光片段由端上或客户端模型产出**，随请求带上，其准确率与失败模式由端侧决定，服务端只能做区间合法性校正
- **BPM、BPM 修正系数、副歌起点与校正点、节奏标记点来自音乐元数据**，由离线流程生产，服务端只消费并按可信区间过滤
- **变速曲线的切分与时长换算由内部计算服务远程完成**，调用超时或返回异常时放弃变速而不是让请求失败
- **模板数据从 KV 缓存读取**，自定义套件按类型整体替换后在同一份副本上生效，模板本身不被修改
- **渲染在客户端完成**，服务端下发工程描述后不再参与，无法验证描述与最终成片的一致性
